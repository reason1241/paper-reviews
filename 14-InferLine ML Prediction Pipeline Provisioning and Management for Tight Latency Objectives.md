# InferLine: ML Prediction Pipeline Provisioning and Management for Tight Latency Objectives

Date: 2026-09-26

- [Link](https://arxiv.org/abs/1812.01776)

- Problem: ML prediction serving pipelines consist of multiple models running on heterogeneous hardware accelerators, and meeting end-to-end tail latency requirements is complicated by the interaction between hardware choice, batch size, and changing query arrival patterns. At the time of the paper, existing systems did not automate pipeline provisioning and configuration to meet tail latency SLOs in a cost-aware manner.
- Solution: The authors introduce InferLine, which consists of a low-frequency combinatorial planner and a high-frequency auto-scaling tuner.
- Claimed technical contributions:
  - The planner uses individual stage profiles and a discrete-event simulator to estimate end-to-end latency, including queueing delays, using a sample query trace. It selects hardware types, the number of replicas, and batch sizes to meet the SLO at low cost. It uses a combinatorial greedy heuristic, initializing each stage with batch size one and the lowest-latency hardware. It rejects the pipeline if the sum of model execution times along the longest path exceeds the SLO; otherwise, it adds replicas to bottleneck stages until the configuration meets the SLO. For cost minimization, the planner considers three actions: increasing batch sizes, removing replicas, and downgrading hardware, while rejecting configurations that violate the SLO. Per-stage scale factors capture the fraction of queries visiting each model, allowing the tuner to scale individual stages rather than the entire pipeline.
  - The tuner monitors incoming pipeline traffic across multiple window durations, starting at the pipeline service time and doubling up to 60 seconds. It detects changes in burstiness using smaller windows and sustained arrival-rate changes using larger windows. It compares the current traffic envelope, which records the maximum number of queries within each window duration, with the planning-trace envelope. When the current envelope exceeds the planning envelope, it determines the required replica counts using the triggering arrival rate, per-model throughput, scale factors, and provisioning ratios.
  - The planner determines the overall hardware, batching, and replication configuration, while the tuner adjusts replica counts to handle unexpected workload changes.
- Metrics / Baselines:
  - The authors evaluate four prediction pipelines on AWS CPU and NVIDIA K80 GPU resources using synthetic and real-workload-derived arrival traces. Metrics include resource cost, tail latency, and latency SLO miss rate.
  - Baselines are coarse-grained configurations that replicate the entire pipeline, provisioned for either the mean request rate (CG-Mean) or peak request rate (CG-Peak), with AutoScale-based tuning.
  - For Image Processing and Video Monitoring with a 150 ms SLO, InferLine’s Planner achieves up to 7.6× lower cost than the coarse-grained baselines while maintaining near-zero SLO miss rates (Figure 5).
  - On the Social Media pipeline’s Slowly Varying trace with a 150 ms SLO, InferLine achieves 99.3% SLO attainment versus 75.8% for the coarse-grained baseline, corresponding to a 34.5× lower miss rate. Total trace costs are $15.27 and $24.63, respectively (Figure 6).
- Key insight and enabling idea: Different pipeline stages have different hardware, batching, and capacity requirements, making stage-specific provisioning and scaling more cost-efficient than replicating the entire pipeline. InferLine combines stage profiling and pipeline simulation to find a low-cost configuration that meets the end-to-end tail latency SLO, then uses traffic envelopes across multiple timescales to detect unexpected workload changes and adjust per-stage replica counts. Separating slow configuration optimization from fast adaptation makes this approach practical.
- Novelty and impact: To the authors’ knowledge, InferLine is the first system to automate ML prediction pipeline provisioning and configuration to meet specified end-to-end tail latency SLOs in a cost-aware manner. It combines stage-level hardware, batching, and replication choices with simulation-based planning and traffic-envelope-based scaling. Its evaluation demonstrates that this approach can reduce resource cost while maintaining high SLO attainment under changing workloads, and can operate across different prediction-serving frameworks.
- Technical Qualities:
  - Framing and assumptions: The paper clearly frames provisioning as a tradeoff between resource cost and end-to-end tail latency, accounting for hardware heterogeneity, batching, queueing, and conditional execution. The Planner assumes that hardware latency ordering remains consistent across batch sizes and that model inference latency is independent of input. The approach also depends on representative profiling and planning samples, and requires a serving framework that supports configurable batching, runtime replica scaling, and centralized per-model queues.
  - Merits of the technical contributions: Individual stage profiling and discrete-event simulation allow the Planner to evaluate configurations without repeatedly deploying the entire pipeline. Stage-specific configuration avoids unnecessary provisioning of lightly used stages, while multi-timescale traffic envelopes detect changes in both arrival rate and burstiness. Separating configuration optimization from rapid replica scaling provides a practical balance between cost efficiency and responsiveness.
  - Does the evaluation support claims and reveal limitations of the proposed approach?: The evaluation supports the cost and SLO-attainment claims across four pipelines, synthetic and real-workload-derived traces, and two serving frameworks. Estimator accuracy tests and Planner/Tuner ablations strengthen the evidence for the design. However, the real-workload-derived traces use sampled inter-arrival times rather than complete original request traces. The greedy Planner occasionally produces suboptimal configurations, and the evaluation does not directly test violations of the hardware-ordering and input-independent-latency assumptions discussed in Section 9.
- Criticism:
  - The greedy Planner occasionally produces suboptimal configurations and does not guarantee a globally minimum-cost solution.
  - The evaluation does not directly test violations of the assumptions that hardware latency ordering remains consistent across batch sizes and that inference latency is independent of input.
  - SLO feasibility depends on the sample planning trace and the accuracy of the performance model. Unexpected workload changes and replica activation delays limit the ability to guarantee SLO attainment during live serving.
  - The paper does not describe or evaluate recovery from Planner or Tuner failures, leaving the availability of its management components unclear.
  - The paper does not evaluate model colocation on shared GPUs or account for the resulting interference when selecting configurations.
  - The Tuner uses scale factors estimated during profiling, without describing how they are updated online. Changes in conditional routing probabilities could therefore increase a stage’s demand without changing the pipeline arrival rate monitored by the Tuner.
