# Serving DNNs like Clockwork: Performance Predictability from the Bottom Up

Date: 2026-09-25

- [Link](https://www.usenix.org/conference/osdi20/presentation/gujarati)

- Problem: Machine learning inference is becoming more important in interactive applications and must consistently meet low-latency SLOs, while existing model-serving systems cannot effectively curtail tail latency caused by unpredictable execution times.
- Solution: The authors propose a distributed model serving system called Clockwork, which mitigates tail latency. 
- Claimed technical contributions:
  - The authors observed that Deep Neural Network (DNN) inference with a fixed execution plan is highly predictable in isolation. However, unpredictability arises at the hardware level (e.g., scheduling concurrent CUDA kernels), OS level (e.g., memory and thread management), and application level (e.g., cache management), as well as from external factors (e.g., shared network bottlenecks and thermal throttling). By consolidating performance-related choices in a centralized controller, the authors reduce internal sources of variability while tolerating occasional external delays.
  - Clockwork consists of a controller and workers. The controller maintains per-model request queues and a scheduler. It maintains performance profiles based on recent action durations for each worker, model, and batch size, and tracks outstanding actions and memory state at every worker. This information is used to predict request completion times, accounting for queueing, model loading when necessary, and execution. The scheduler assigns requests to workers, selects deadline-feasible batch sizes, and explicitly schedules LOAD, UNLOAD, and INFER actions.
  - Each worker stores all models in host RAM and loads model weights into GPU memory when necessary, as directed by the controller. Workers preallocate GPU memory for intermediate results in Workspace, inputs and outputs in IOCache, and model weights in PageCache.
  - To reduce variability, each worker executes only one inference batch at a time per GPU while overlapping execution with weight loading and input/output transfers, which have negligible interference in the evaluated workloads. 
  - Each action has an earliest and latest permitted start time. Actions that cannot start within this window are treated as errors and canceled, allowing workers to return to the schedule without propagating delays to subsequent actions.
- Metrics / Baselines:
  - The authors evaluate 61 DNN models on NVIDIA V100 GPUs using controlled workloads and a Microsoft Azure Functions (MAF) trace-derived workload. Metrics include goodput (successful requests completed within their SLO), request latency, workload satisfaction (goodput divided by offered load), and action-timing prediction error.
  - With 15 ResNet50 instances on one GPU, Clockwork maintains useful goodput at SLOs below 100 ms, while Clipper and INFaaS deteriorate sharply. INFaaS runs on different infrastructure, so its comparison is qualitative (Figure 5).
  - In a six-hour MAF-derived workload with 4,026 model instances on 12 workers and a 100 ms SLO, Clockwork processes approximately 208 million requests, with 58 action-timing failures and no request timeouts. Average goodput is 9,638 requests/s (Figure 9 and §6.5).
  - The controller reaches 103,387 requests/s with 110 emulated workers before becoming the bottleneck. This experiment uses simulated action durations and zero-length inputs, so it measures controller scalability rather than full GPU-serving throughput (Figure 11).
- Key insight and enabling idea: DNN inference with a fixed execution plan is highly predictable, while much of the execution-time variability comes from scheduling, concurrency, and memory-management decisions across system layers. Clockwork consolidates these choices in a centralized controller, preserving predictable worker execution and enabling proactive scheduling to meet request deadlines.
- Novelty and impact: Clockwork’s main contribution is a system design that preserves the predictability of individual DNN inferences throughout a distributed serving system. It consolidates scheduling and memory management choices in a centralized controller and treats missed action-start windows as errors to prevent cascading delays. Its evaluation demonstrates that this approach can support thousands of models while maintaining tight latency targets and useful goodput.
- Technical Qualities:
  - Framing and assumptions: The paper frames tail latency as partly caused by internal system choices that can be controlled. It assumes predictable DNN execution for known models and batch sizes, dedicated worker machines and GPUs, mostly predictable network latency, and limited interference between weight transfers and GPU execution. Models are preloaded into host RAM, and user-defined preprocessing and postprocessing are excluded.
  - Merits of the technical contributions: The controller combines execution profiles with explicit knowledge of worker memory and pending actions to schedule model loading, batching, and inference before request deadlines. Explicit action-start windows limit delay propagation, while overlapping transfers with execution improves resource use. These mechanisms enable latency-sensitive and background workloads to share GPUs with stable response times.
  - Does the evaluation support claims and reveal limitations of the proposed approach?: Controlled experiments and the MAF-derived workload support the claims of predictable execution, tight latency targets, and serving thousands of models. However, INFaaS runs on different infrastructure, the MAF workload is derived from function arrivals rather than actual inference requests, and the controller scalability experiment uses emulated workers with zero-length inputs. The evaluation does not establish security isolation or fault tolerance.
- Criticism:
  - INFaaS runs on different infrastructure, so the comparison does not isolate the effects of the serving-system design from hardware and deployment differences.
  - The centralized controller eventually becomes a bottleneck, reaching peak goodput at 110 emulated workers. The prototype also routes all inputs and outputs through the controller, introducing a potential network bottleneck.
  - The MAF workload is derived from function arrivals rather than actual inference requests, limiting how directly the results represent production model-serving workloads.
  - The controller scalability experiment uses emulated workers with zero-length inputs, so it does not demonstrate full end-to-end serving performance at that scale.
  - The evaluation does not establish security isolation or fault tolerance, leaving important requirements for production deployment unverified.
  - Clockwork assumes dedicated worker machines and GPUs and mostly predictable network latency. Its effectiveness under shared-resource interference remains unestablished.
