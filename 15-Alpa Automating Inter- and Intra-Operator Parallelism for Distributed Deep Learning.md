# Alpa: Automating Inter- and Intra-Operator Parallelism for Distributed Deep Learning

Date: 2026-09-27

- [Link](https://arxiv.org/abs/2201.12023)

- Problem: Existing model-parallel training systems either require users to manually create a parallelization plan or automatically generate one from a limited space of model parallelism configurations.
- Solution: The authors propose a new compiler called Alpa, which automatically generates parallel training execution plans covering data, operator, and pipeline parallelism.
- Claimed technical contributions:
  - Alpa generates model-parallel execution plans by hierarchically optimizing the plan at two different levels: intra-op and inter-op parallelism.
  - The inter-op pass uses dynamic programming (DP) to assign stages to meshes and invokes the intra-op compilation pass on each candidate stage-mesh pair to obtain its execution plan. This pass minimizes the end-to-end pipeline execution latency for the entire computational graph. For this, the authors group operators into stages and optimize device mesh assignments and shapes from a restricted candidate set. The DP has two structural constraints: 1) colocating corresponding forward and backward operators on the same submesh and 2) using sliced submeshes to fully cover all devices. Candidate stage plans are compiled and profiled to obtain their latency and memory requirements, and plans exceeding device memory are excluded. The modeled pipeline latency is the sum of each stage's forward and backward latency + (the number of microbatches - 1) * the slowest stage latency. The DP also uses performance optimization techniques such as early pruning and operator clustering.
  - At the intra-op level, Alpa minimizes the cost of executing a stage (i.e., subgraph) of the computational graph on its assigned device mesh using an integer linear programming (ILP) formulation. The authors define sharding specs, which describe tensor layouts, and several parallel algorithms using these specs. The ILP considers enumerated candidate parallel algorithms and their input-output sharding layouts, so that Alpa can jointly select algorithms across operators in a stage while considering resharding costs. To solve the ILP, they estimate communication costs, including resharding costs, by dividing the number of communicated bytes by the corresponding mesh dimension bandwidth. They set compute costs to zero because heavy operators evenly divide arithmetic work across devices, while lightweight operators have negligible computation costs. They also merge lightweight operators, such as element-wise operators, to simplify the graph.
  - A runtime orchestration pass fulfills the communication requirements between stages on different meshes and generates static execution instructions. Within-mesh collective communication primitives are inserted when compiling each stage. For cross-mesh resharding, Alpa generates send/receive operations and applies local all-gather when the destination layout requires replication. This avoids repeatedly sending the same tensor pieces over slow cross-mesh connections by distributing them over the fast local network instead. Alpa uses single program, multiple data (SPMD) within each stage mesh and multiple program, multiple data (MPMD) across stage meshes.
- Metrics / Baselines:
  - The authors evaluate GPT, GShard MoE, and Wide-ResNet on up to 64 NVIDIA V100 16-GB GPUs across eight AWS servers, with NVLink within servers and 25-Gbps cross-server bandwidth. The main metric is aggregate training throughput in PFLOPS, measured using dummy data after warmup. They evaluate weak scaling by increasing model size with GPU count.
  - End-to-end baselines are grid-searched Megatron-LM v2 for GPT, grid-searched DeepSpeed for MoE, and an Alpa-based pipeline-plus-data-parallel baseline (PP-DP) for Wide-ResNet. They also compare intra-op-only and inter-op-only configurations.
  - Alpa broadly matches Megatron-LM on GPT, achieves 3.5× and 9.7× higher throughput than DeepSpeed on MoE with 16 and 32 GPUs, respectively, and reaches approximately 80% linear scaling efficiency on Wide-ResNet with 32 GPUs. The evaluated DeepSpeed configuration does not include pipeline parallelism (Figure 7).
  - Ablations compare the intra-op optimizer with data parallelism, ZeRO-2, ZeRO-3, and heuristic sharding, and the inter-op optimizer with equal-operator clustering and equal-layer stage partitioning. They also measure compilation time and the throughput benefit of local all-gather for cross-mesh resharding (Figures 8–11).
- Key insight and enabling idea: Intra-op and inter-op parallelism have different communication patterns that match the hierarchical network structure of a GPU cluster. Intra-op parallelism requires frequent collective communication and benefits from high-bandwidth connections within device meshes, while inter-op parallelism communicates between stages and can use slower cross-mesh connections when stage boundaries limit communication. This enables hierarchical optimization: the intra-op optimizer finds an efficient plan for each candidate stage-mesh pair, and the inter-op optimizer uses its execution cost to choose stage boundaries and device assignments.
- Novelty and impact: Alpa automates parallel training through a compiler that hierarchically combines intra-op and inter-op optimization. Unlike systems with limited search spaces or manually designed strategies, it jointly selects stage boundaries, device mesh assignments, and per-operator sharding plans. This reduces manual tuning and supports different model architectures and cluster configurations, while matching or outperforming specialized systems in the evaluated settings.
- Technical Qualities:
  - Framing and assumptions: Alpa frames parallel training as hierarchical optimization that matches intra-op and inter-op communication patterns to the cluster’s bandwidth hierarchy. It requires static computation graphs with known tensor shapes and assumes equivalent compute capability within each mesh. The ILP treats heavy operators’ compute costs as similar across candidate strategies, while the inter-op optimizer assumes cross-stage communication is small and omits its cost. Pipeline planning uses a static linear schedule.
  - Merits of the technical contributions: Automated planning reduces manual tuning, allowing developers to focus more on model innovation. Flexible stage boundaries, mesh assignments, and per-operator sharding support heterogeneous model architectures. Hierarchical optimization makes the search tractable, while local all-gather reduces redundant communication over slow cross-mesh connections.
  - Does the evaluation support claims and reveal limitations of the proposed approach?: Comparisons across GPT, MoE, and Wide-ResNet, together with optimizer and runtime ablations, support the effectiveness of the approach in the tested settings. However, the main experiments measure weak scaling by increasing model size with GPU count, rather than scaling a fixed model. Evaluation on one cluster configuration does not establish robustness across network topologies or directly test the assumption that cross-stage communication is small.
- Criticism:
  - The main experiments measure weak scaling by increasing model size with GPU count, rather than scaling a fixed model (strong scaling).
  - Evaluation on one cluster configuration does not establish robustness across network topologies.
  - Although the authors evaluate cross-mesh communication overhead, they do not directly test how omitting cross-stage communication costs affects the quality of the selected plans.
  - The intra-op approach assumes equivalent compute capability within each mesh, limiting support for heterogeneous devices within a mesh.
  - Alpa requires static computation graphs with known tensor shapes, and its inter-op optimizer does not explore schedules that execute independent graph branches concurrently on different meshes.
