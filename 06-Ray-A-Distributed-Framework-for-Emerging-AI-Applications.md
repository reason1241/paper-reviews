# Ray: A Distributed Framework for Emerging AI Applications

Date: 2026-09-08

- [Link](https://www.usenix.org/conference/osdi18/presentation/moritz)

- Problem: Emerging AI applications, particularly reinforcement learning (RL), require continuous interaction between agents and environments to learn and act. Efficiently supporting their tightly coupled training, simulation, and serving workloads requires fine-grained, heterogeneous computations (e.g., millisecond-scale tasks with different CPU/GPU requirements), a flexible computation model (supporting both stateless and stateful computations), and dynamic execution (e.g., running additional simulations based on previous results). The authors argue that existing frameworks do not efficiently satisfy all these requirements together.
- Solution: They introduce Ray, a distributed system that supports task-parallel (stateless) and actor-based (stateful) computations through a unified dynamic execution engine. Ray uses a distributed scheduler, a distributed key-value store for control metadata (the Global Control Store), and a distributed object store for task inputs and outputs.
- Claimed technical contributions:
  - They unify task-parallel and actor-based programming using tasks, actors, and futures. For the computation model, Ray employs a dynamic task graph with data edges for input/output dependencies between objects and tasks, control edges for task invocations through nested remote calls, and stateful edges for dependencies between successive method invocations on the same actor.
  - Architecturally, they adopt two layers: an application layer implementing the programming API and a system layer providing scalability and fault tolerance. The application layer consists of three types of processes: drivers (executing user programs), workers (executing stateless tasks), and actors (executing stateful computations, such as parameter-server operations). The system layer has three components: the Global Control Store (GCS, a sharded key-value store with per-shard chain replication for control state, including object metadata and task lineage), a bottom-up distributed scheduler (a two-level hierarchy that schedules locally first and globally if needed), and an in-memory distributed object store (using shared memory within each node for task inputs and outputs; each individual object fits on one node but can be replicated across nodes). Separating control-state storage from scheduling and data-management logic enables these components to scale independently and simplifies recovery.
- Metrics / Baselines:
  - They evaluated locality-aware task placement (task latency versus input size, with and without locality awareness), end-to-end scalability (tasks per second versus cluster size), object-store performance (IOPS and write throughput), GCS fault tolerance (read/write latency during replica failure and replacement), GCS flushing (memory usage with and without flushing to disk), and recovery from task and actor failures (throughput during failure and recovery). Ray exceeded 1.8 million tasks per second on independent empty tasks. They also compared allreduce completion time against OpenMPI: Ray performed better for large objects, while OpenMPI performed better for smaller objects.
  - For distributed training, they compared Horovod + TF, distributed TF, and Ray + TF using the same ResNet-101 model and synthetic data, measuring images per second. Ray matched Horovod and was within 10% of distributed TensorFlow. For serving, they measured states per second against Clipper in a colocated setting; Ray achieved higher throughput, benefiting from low-overhead serialization and shared memory compared with Clipper’s REST interface. For simulation, they measured timesteps per second against a BSP-style MPI implementation; Ray’s asynchronous execution achieved up to 1.8× higher throughput for variable-duration simulations.
  - For complete RL applications, they implemented existing Evolution Strategies (ES) and Proximal Policy Optimization (PPO) algorithms using Ray and measured time to reach a score of 6000 on Humanoid-v1. For ES, they compared against a specialized Redis/multiprocessing implementation. Ray used a tree of aggregation actors to avoid a driver bottleneck, scaled to 8192 CPU cores, and achieved a median time of 3.7 minutes versus the best published result of 10 minutes. For PPO, they compared against an optimized MPI-based implementation. Ray achieved faster training with fewer GPUs by separating CPU simulation work from GPU training and collecting simulation results asynchronously.
- Key insight and enabling idea: RL applications tightly couple workloads with different execution needs: stateless tasks benefit from flexible scheduling, while stateful computations benefit from keeping state near the computation. Ray’s enabling idea is to unify tasks and actors in one dynamic computation graph, allowing these workloads to interact efficiently. A shared control store and distributed scheduling support this flexibility at scale without requiring a separate distributed system for each RL algorithm.
- Novelty and impact: Ray’s novelty lies in integrating task-parallel and actor-based computation into a unified dynamic execution engine, supported by a shared control store and bottom-up distributed scheduling. Although these individual ideas build on prior work, their integration enables tightly coupled training, simulation, and serving within one framework. The paper demonstrates that a general-purpose system can achieve performance competitive with specialized RL implementations while reducing the need for application-specific distributed-systems code.
- Technical Qualities:
  - Framing and assumptions: The paper clearly motivates Ray through tightly coupled training, simulation, and serving workloads that require fine-grained, heterogeneous, and dynamic execution. Its recovery model relies on stateless tasks being deterministic and side-effect free, while actors require checkpointing for efficient recovery. These assumptions can require care when handling stochastic simulations or external side effects.
  - Merits of the technical contributions: Unifying tasks and actors supports both flexible task placement and efficient stateful computation. Separating control-state storage from scheduling and data management allows these components to scale independently, while bottom-up scheduling reduces reliance on a global scheduler. The ES and PPO implementations demonstrate how these mechanisms enable application-level optimizations.
  - Does the evaluation support claims and reveal limitations of the proposed approach?: The evaluation supports Ray’s feasibility and competitive performance through microbenchmarks and complete RL applications. It also reveals some limitations, such as poorer allreduce performance for small objects. However, the independent empty-task benchmark does not establish scalability for complex dependency graphs, and limited architectural ablations make individual design benefits difficult to isolate. GCS failure testing covers a narrow scenario, and a controlled comparison with closely related frameworks such as Dask would strengthen the evidence.
- Criticism:
  - The 1.8-million-tasks-per-second result uses independent empty tasks, so it does not establish comparable scalability for workloads with complex dependencies and substantial data transfers.
  - The paper measures the complete Ray system but does not directly compare its bottom-up scheduler with a global-first scheduler, or its GCS-based metadata design with scheduler-owned metadata. Consequently, the individual performance benefits of these architectural choices remain unclear. Dynamic execution is demonstrated through applications, but its performance under varying graph structures is not systematically evaluated.
  - GCS replica failure is tested, but chain-master recovery and behavior under broader failures are insufficiently explained. Long-running lineage storage and garbage collection also remain concerns.
  - MPI-based application comparisons are useful, but differences in synchronization and resource allocation limit conclusions about the underlying systems. A controlled comparison with Dask or CIEL would strengthen the paper’s claims.
