# INFaaS: Automated Model-less Inference Serving

Date: 2026-09-24

- [Link](https://www.usenix.org/conference/atc21/presentation/romero)

- Problem: Inference applications have diverse accuracy and latency requirements, while query load changes over time. Existing serving systems require developers to choose model variants and hardware in advance; even when they autoscale VMs or replicas, they typically keep that choice fixed, making cost-efficient adaptation and SLO-aware resource sharing difficult.
- Solution: They propose INFaaS, an automated model-less system for distributed inference serving, where developers simply specify the performance and accuracy requirements for their applications without needing to specify a specific model-variant for each query. 
- Claimed technical contributions:
  - INFaaS addresses (1) diverse application requirements for latency, cost, and accuracy, (2) heterogeneous execution environments, and (3) diverse model variants through a serving architecture comprising a controller, workers, a variant generator and profiler, a model-variant selection policy, a metadata store, and an S3 model repository.
  - Declarative APIs support model registration and query submission. After registering trained models, developers can submit a query with an application ID and latency and accuracy requirements without naming a specific model variant. They may also specify a registered model directly. INFaaS selects a suitable variant for the query.
  - The controller contains a dispatcher, VM autoscaler, and model registrar. The dispatcher selects a model variant and worker for each query using the selection policy. The VM autoscaler changes the number of workers based on load and resource utilization. The model registrar handles registration.
  - Each worker has a dispatcher, hardware-specific executors, a model autoscaler, and a monitoring daemon. The dispatcher forwards a query to the selected variant instance, and the executor runs it. The model autoscaler responds to load changes by replicating a running variant or switching to a different one. The monitoring daemon tracks utilization and performance degradation to support SLO-aware resource sharing.
  - The variant generator creates versions of registered models using different batch sizes, hardware resources, hardware-specific settings, and graph optimizers. The profiler measures properties such as loading latency, inference latency, and peak memory use; INFaaS also records variant accuracy using a validation set.
  - The model-variant selection policy is invoked when a query arrives and when load changes. For a query, it prefers a suitable active variant and selects a lightly loaded worker; it avoids overloaded or interfered instances. For scaling, the authors formulate an integer linear program that accounts for throughput, latency, resource limits, hardware cost, and model-loading time. Because solving it is too slow, INFaaS uses a greedy heuristic that compares replication with switching variants and coordinates with the controller when more worker capacity is needed.
  - The metadata store uses Redis on the controller machine. It stores static variant information, such as profiled latency and accuracy, and dynamic information, such as worker resource usage, query load, and variant state.
- Metrics / Baselines:
  - The authors evaluated 175 variants from 22 model architectures on AWS CPU, GPU, and Inferentia workers. They compared INFaaS with Clipper+ (fixed variant instances) and SM+ (replica autoscaling), both implemented in the INFaaS environment.
  - In a mixed-model workload using Twitter trace timings INFaaS achieved 1.1× and 1.3× higher throughput and 1.63× and 2.54× fewer SLO violations than Clipper+ and SM+, respectively. It also reported 1.23× lower cost than Clipper+ (Figure 5).
  - With ResNet50 at 4 QPS, INFaaS cost 21.6× less than GPU-only Clipper+ and 21.3× less than GPU-only SM+. The comparison uses GPU-only baselines at low load; it is not a general cost saving (Figure 6).
  - In the GPU-sharing experiment, INFaaS reduced P99 latency under interference and cost 10% less than Clipper+ (Figure 7). Variant-and-worker selection took a median of 2.2–3.5 ms in the measured cases (Table 7).
- Key insight and enabling idea: What matters to many inference applications is meeting accuracy and latency requirements at low cost, rather than using a particular model variant. INFaaS profiles diverse variants and selects and scales a suitable one as requirements and load change.
- Novelty and impact: INFaaS provides a declarative inference interface: developers specify accuracy and latency requirements instead of choosing a model variant for each query. It combines this with automatic selection and scaling across model variants and CPU, GPU, and Inferentia workers. Its evaluation shows improved throughput and fewer SLO violations than the tested baselines, with lower cost in some settings.
- Technical Qualities:
  - Framing and assumptions: The paper frames inference serving around application accuracy and latency requirements rather than a fixed model variant. It assumes suitable variants have already been registered and profiled, and that the requested accuracy is feasible.
  - Merits of the technical contributions: INFaaS combines a simple query interface with variant selection, model and VM scaling, and resource sharing across heterogeneous hardware. Its ability to switch variants as load changes is the main technical strength.
  - Does the evaluation support claims and reveal limitations of the proposed approach?: The experiments support that this flexibility improves throughput, SLO compliance, and cost in the tested workloads. However, Clipper+ and SM+ are reconstructed baselines, and their fixed variant and batch-size choices affect the comparisons. The large low-load cost saving is measured against GPU-only baselines, so it should not be generalized to all deployments.
- Criticism:
  - Clipper+ and SM+ were reconstructed within INFaaS. Their fixed variant and batch-size choices affect the results; a clearer tuning procedure and comparisons across more baseline configurations would make the evaluation more convincing.
  - The reported 21× cost saving at low load is against GPU-only baselines, so it does not represent the saving over a CPU-configured baseline.
  - The paper describes automatic variant profiling, but the [public implementation](https://github.com/stanford-mast/INFaaS#model-registration) requires users to run the profiler and provide configuration files when registering models.
  - The “Twitter” workload uses Twitter request times to determine when inference queries arrive; it is not a trace from an actual inference service. The authors also ensure that every query’s accuracy requirement can be met by at least one registered model variant, so the experiments do not show how INFaaS performs when users request an accuracy that no available variant can provide.
