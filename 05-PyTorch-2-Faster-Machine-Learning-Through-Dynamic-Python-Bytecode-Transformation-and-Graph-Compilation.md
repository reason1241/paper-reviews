# PyTorch 2: Faster Machine Learning Through Dynamic Python Bytecode Transformation and Graph Compilation

Date: 2026-09-02

- [Link](https://docs.pytorch.org/assets/pytorch2-2.pdf)

- Problem: PyTorch uses eager programming model, which is easier to understand and debug than graph mode frameworks such as TensorFlow. However, this eagar mode frameworks have limited opportunities for graph-level optimizations through compilers because the framework sees only one operator at a time. Existing solutions to graph capture include record/replay, Python parsing, and lazy evaluation, but those sacrifice usability or performance: record/replay can produce incorrect behavior, Python parsing struggles to support the full complexity of Python semantics, and lazy evaluation introduces run-time overheads and additional kernel launch latency.
- Solution: The authors present two extensions: TorchDynamo, a Python-level just-in-time (JIT) compiler that enables graph compilation by dynamically modifying Python bytecode before execution and extracting sequences of PyTorch operations into an FX graph, and TorchInductor, which translates PyTorch programs into OpenAI's Triton for GPUs and C++ for CPUs. TorchDynamo mixes compiled graph fragments with ordinary Python execution through graph breaks, preserving flexibility when code cannot be captured.
- Claimed technical contributions:
  - TorchDynamo
    - This uses the CPython frame evaluation hook and adds mechanisms for graph extraction, dynamic bytecode analysis and transformation, guarding, and caching to reduce recompilation. It checks filenames to determine whether analysis should be skipped, checks for cached compiled bytecode whose guards pass, and, if no valid cached entry exists, performs symbolic analysis of function bytecode to extract an FX graph, guards, and side effects, compiles the FX graph with a user-defined compiler function, generates and compiles a Python function containing guards, generates graph breaks and new bytecode when needed, installs the generated Python bytecode and guard function in the cache, and executes it.
    - The authors added guards for safe reuse of compiled artifacts, symbolic evaluation to analyze Python bytecode and construct FX graphs, and modeling of Python data structures (e.g., TensorVariable, ConstDictVariable, and ListVariable) for symbolic evaluation. They also implemented bytecode analysis to handle inlining, control flow, closures, side effects, graph breaks (unsupported operations are executed in Python), and continuation functions. In addition, compiler backends such as TorchInductor use the reusable AOTAutograd component, which runs autograd with fake tensor inputs, records a joint forward and backward graph, and applies a min-cut algorithm to split it into forward and backward graphs while optimizing memory usage, including selectively recomputing cheap activations instead of saving them.
  - TorchInductor
    - This supports decomposition through AOTAutograd, which rewrites PyTorch operators into simpler primitive operators that are easier to lower (Section 4.2); lowers FX graphs into a define-by-run loop-level IR using symbolic sizes and indices; performs scheduling for operator fusion, kernel ordering, and memory planning; generates Triton code for GPUs and C++/OpenMP code for CPUs; and generates wrapper code to call kernels from Triton, C++, and external sources.
  - Dynamic Shapes
    - Input or intermediate tensor shapes may vary across runs, such as changing batch size or sequence length, data-dependent outputs in detection models, and sparse representations such as sparse tensors, jagged tensors, and graph neural networks. Static-shape compilers would need to recompile for each new shape. PyTorch 2 supports dynamic shapes using symbolic sizes and symbolic shape guards. For shape-dependent control flow, TorchDynamo specializes to one control-flow path using the concrete size observed during JIT compilation, then adds guards so the compiled trace is reused only when its assumptions remain valid. Meta functions propagate output shape information without performing the actual tensor computation, allowing intermediate sizes to be expressed in terms of input sizes. The system also applies 0/1 specialization and symbolic-expression simplification to reduce guard and reasoning overhead. Data-dependent sizes can produce unbacked symbolic integers, whose concrete values are unavailable during tracing; control flow depending on these values requires graph breaks in the system described by the paper.  However, it does not support dynamic-rank programs, where the number of tensor dimensions itself changes across executions.
- Metrics / Baselines:
  - Graph capture: On float32 inference benchmarks from TorchBench, HuggingFace, and TIMM using an NVIDIA A100 GPU, TorchDynamo supports more models than TorchScript, especially on TorchBench and HuggingFace. Its ability to capture partial graphs and fall back to Python avoids TorchScript’s all-or-nothing capture limitation.
  - Graph-capture overhead: On float32 TorchBench models using an NVIDIA V100 GPU, TorchDynamo adds 5% inference and 1% training overhead, compared with 38% and 90% for Lazy Tensors. Lazy Tensors repeatedly builds graphs and delays kernel execution; cross-iteration pipelining reduces these overheads only slightly.
  - Compiler performance: Across the three suites, GPU float32/float16 and CPU float32 experiments compare geometric mean speedup over eager PyTorch against nvFuser, NNC, PyTorch/XLA, ONNX Runtime, TVM, and Hidet, using TorchDynamo for graph capture. TorchInductor is faster in most cases; other backends suffer from limited optimization coverage, unsupported operators, or large slowdowns on some models, although speedup averages include only each backend’s working models.
  - Sources of speedups: An ablation study on float16 HuggingFace models using an NVIDIA A100 GPU identifies fusion and inlining as the largest sources of improvement because they reduce memory traffic. Disabling both turns speedups into slowdowns, as decomposed primitive operations are no longer combined into efficient kernels.
- Key insight and enabling idea: Graph compilation does not require capturing the entire Python program. TorchDynamo uses guarded bytecode transformation to extract compilable graph fragments while allowing unsupported code to execute normally in Python, preserving usability while enabling optimization. TorchInductor then uses a define-by-run loop-level IR aligned with PyTorch’s semantics to fuse operations and generate efficient GPU and CPU code.
- Novelty and impact: The main novelty is combining guarded Python bytecode transformation and partial graph capture with a PyTorch-aligned, define-by-run loop-level IR, enabling compilation without requiring users to rewrite their entire models into a restricted programming model. These components power torch.compile in PyTorch 2, bringing compiler optimizations to existing eager-mode programs; the paper reports geometric mean speedups of 2.27× for inference and 1.41× for training on an NVIDIA A100 GPU across 180+ real-world models.
- Technical Qualities:
  - Framing and assumptions: The paper clearly frames the challenge as enabling compiler optimizations while preserving Python’s flexibility. The approach relies on guarded reuse of specialized graphs to amortize compilation costs, while graph breaks handle unsupported code; dynamic rank remains unsupported.
  - Merits of the technical contributions: TorchDynamo’s partial graph capture avoids all-or-nothing compilation, and guards allow compiled code to be reused safely. TorchInductor’s PyTorch-aligned IR simplifies support for tensor semantics, while fusion and inlining reduce memory traffic.
  - Does the evaluation support claims and reveal limitations of the proposed approach?: The evaluation supports improved model coverage, low steady-state capture overhead, and faster execution through comparisons across three benchmark suites and optimization ablations. However, the evaluation measures steady-state performance after warm-up and does not separately report initial compilation time.
- Criticism:
  - The evaluation does not separately report initial compilation time or how many executions are needed to recover that cost, making the benefit for short-running workloads unclear.
  - Speedup averages include only each backend’s working models, so they cover different model subsets. Reporting model coverage helps, but a comparison on a shared subset would make relative performance easier to assess.
  - Although dynamic-shape support is a technical contribution, the evaluation does not directly measure performance or recompilation frequency under changing input shapes.
  - The paper reports graph-break counts but does not isolate their performance impact, leaving unclear how much frequent fallback to Python limits optimization benefits.
